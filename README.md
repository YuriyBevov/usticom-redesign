# Разработка и обновление сайта Юстиком

Рабочий сайт состоит из кода приложения, Битрикса, базы данных и изменяемых файлов.
GitHub Actions проверяет pull request в `main` и собирает готовый релиз.
После включения доставки изменения в `main` обновляют только код из разрешённого списка.
База, загрузки и содержимое редактируемых областей сохраняются на сервере.

Рабочие инструкции: [границы обновления](#точный-состав-обновления),
[правила для администраторов](#правила-для-администраторов),
[синхронизация разработчиком](#что-разработчик-синхронизирует-отдельно),
[проверки перед публикацией](#проверки-разработчика-перед-публикацией)
и [проверки после публикации](#проверки-разработчика-после-публикации).

## Локальная разработка

Используйте Node.js 22.12 или новее, PHP CLI 8.2 или новее и Python 3.10 или новее.
Локальному PHP нужен параметр `short_open_tag=On`, поскольку сайт использует короткие PHP-теги.

```sh
git switch main
git pull --ff-only
git switch -c feature/название-задачи
npm ci
npm run setup:content
npm run build
npm test
git push -u origin feature/название-задачи
```

`setup:content` создаёт только отсутствующие файлы из `deploy/defaults`.
Телефон, почта и адрес в начальных значениях — заглушки для локальной разработки.
Для полноценного сайта восстановите Битрикс, базу, `/upload/` и серверный `/include/`
из согласованной резервной копии. Git не заменяет резервную копию сайта.

Завершённую задачу отправляйте pull request в `main`. После успешного `Build and test`
слияние запускает доставку на боевой сервер, если `PRODUCTION_DEPLOY_ENABLED=true`.
Обычные push в рабочие ветки сайт не обновляют. Проверки запускаются при открытии и обновлении pull request.

## Код и редактируемый контент

| Содержимое | Где хранится и как обновляется |
| --- | --- |
| Шаблоны, компоненты, обработчики PHP, JS, SCSS, изображения оформления | Git; автоматически обновляются |
| `_dist` с манифестом, CSS и JS | Собирается в CI; входит в архив релиза |
| Контент инфоблоков, заявки, пользователи и настройки | База сервера; не импортируется при доставке кода |
| Изображения и документы из админки | `/upload/`; не заменяется при доставке |
| Тексты областей, логотипы, контакты | `/include/`; существующие файлы не заменяются |
| Статические меню, `.section.php`, `urlrewrite.php`, `robots.txt` | Сервер; начальные значения создаются только при отсутствии |
| Sitemap XML | Формируется Битриксом на сервере; не доставляется из локального проекта |
| Ключи, пароли, `.env`, настройки подключения к БД | Сервер или GitHub Secrets; не входят в релиз |

Правила релиза находятся в `deploy/policy.json`. Скрипт дополнительно проверяет защищённые пути.
В `deploy/defaults` лежат начальные значения, а не актуальный серверный контент.
Изменение defaults не обновляет уже существующий файл на сервере.

Редактируемые фрагменты страницы «О компании», страницы опыта и логотипы перенесены
из шаблона в `/include/`. При первом релизе отсутствующий файл копируется из соответствующего
старого пути **на сервере**, чтобы сохранить последние правки редакторов. Если нового и старого
файла нет, используется начальное значение. Пустой существующий файл тоже сохраняется.
Старые фрагменты остаются на диске для проверки и восстановления.

HTML и PHP-разметка блоков остаётся в шаблоне. Контент-менеджерам следует предоставить
редактирование инфоблоков и нужных областей, без редактирования PHP-кода, шаблонов
и параметров компонентов. Номера групп и файловые права настраиваются после проверки сервера.
Если редакторам потребуется менять текст, который ещё записан прямо в `index.php`,
сначала вынесите этот текст в инфоблок или отдельную область.

Статические меню можно редактировать через админку; динамическое меню услуг формируется
из инфоблока, а его программные файлы `*.menu_ext.php` обновляются из Git.
Новые маршруты добавляются отдельно с сохранением существующего `urlrewrite.php`.
Структуру инфоблоков и новые свойства меняйте отдельными проверенными миграциями;
автоматический деплой их не запускает. Дамп локальной базы на рабочую базу не импортируйте.

Старые каталоги `__local`, `_about`, другие архивные разделы и файлы с `copy` пока
сохранены в Git для проверки зависимостей после восстановления. Они не входят в релиз.
Не удаляйте их на сервере, пока не проверены привязки шаблонов и ссылки в базе.

## Точный состав обновления

Доставка собирает разрешённые **отслеживаемые Git файлы**, добавляет свежий `_dist`
и устанавливает только изменившиеся файлы. Наличие файла в локальном каталоге
или даже в Git само по себе не означает, что он попадёт на сервер.
Фактические правила определены в [deploy/policy.json](deploy/policy.json),
[deploy/release.py](deploy/release.py) и защитной проверке
[deploy/remote.py](deploy/remote.py). При расширении состава релиза разработчик
должен согласованно обновить упаковщик, серверную проверку разрешённых путей и тесты.

| Часть проекта | Как попадает на сервер | Кто изменяет |
| --- | --- | --- |
| `local/templates/littleweb/`: шаблоны, компоненты, PHP-разметка, JS, SCSS, изображения оформления | Из Git, кроме специально исключённых редактируемых фрагментов | Разработчик через репозиторий |
| `local/templates/littleweb/_dist/` | Сборка Vite в Actions; локальная сборка не отправляется в Git | Разработчик меняет исходники; CI собирает результат |
| `local/php_interface/`, включая `init.php`, вспомогательные функции и файлы миграций | Из Git; наличие файла миграции не запускает её | Разработчик |
| `local/ajax/` | Из Git | Разработчик |
| Корневые `index.php`, `404.php` | Из Git | Разработчик |
| `index.php` в `about`, `cases`, `contacts`, `events`, `experiences`, `news`, `partnership`, `prices`, `privacy-policy`, `publications`, `services`, `sitemap` | Из Git | Разработчик |
| `.header_services.menu_ext.php`, `services/.left.menu_ext.php` | Из Git; это программные источники динамического меню | Разработчик |
| Фавиконки, `site.webmanifest`, изображения иконок приложения, два HTML-файла подтверждения Google/Яндекса | По списку `code_files` в политике | Разработчик |
| Корневой `/include/`, статические `*.menu.php`, `.section.php`, `robots.txt`, `urlrewrite.php` | Только начальное создание разрешённых файлов из `deploy/defaults`, если файла нет; существующие сохраняются | Контент в согласованных областях — администратор; маршруты и технические изменения — разработчик |
| Инфоблоки, их разделы, элементы, свойства и пользовательские поля; веб-формы, заявки, пользователи, права и настройки Битрикса | Автоматически не переносятся: это база конкретного сайта | Контент — администратор; структура и технические настройки — разработчик |
| `/upload/`, ядро `/bitrix/`, настройки подключения, `.htaccess`, конфигурация PHP/хостинга | Не заменяются релизом | Контентные загрузки — администратор; техническое обслуживание — разработчик/администратор сервера |
| `deploy/`, `.github/workflows/`, `tests/`, документация | Управляют сборкой и проверками в репозитории; служебные скрипты доставки передаются отдельно внутри релиза | Разработчик |
| Новые страницы и каталоги вне разрешённого списка, например отдельная версия `/en/` | Не входят автоматически; сначала нужны правила доставки, маршруты и настройки Битрикса | Разработчик |

Для фрагментов «О компании», страницы опыта и логотипов исключения перечислены
в `legacy_content` и `shared_files` политики. **Не весь**
`local/templates/littleweb/include/` является редактируемым контентом:
например, `hero-section.php` и `section.php` с разметкой блоков обновляются из Git.

`deploy/defaults` — начальные значения, а не механизм синхронизации действующего контента.
Изменение телефона, меню или маршрута только в defaults не обновит уже существующий файл
на рабочем сайте. Пустой существующий файл также не заполняется повторно.

Устаревший файл кода может быть удалён, если он ранее доставлялся этим механизмом
и исчез из нового релиза. Старая хешированная сборка `_dist` сохраняется для страниц
с прежними ссылками. Серверные файлы вне списка управляемого кода не удаляются
этим механизмом доставки.

## Правила для администраторов

### Что можно редактировать

- Тексты, цены, изображения, даты, сортировку и активность элементов и разделов инфоблоков.
- Значения уже настроенных свойств: выбор тиззеров, связанных услуг, цен, FAQ, документов,
  показ в меню и слайдере, тексты SEO-блока. Изменение значения отличается от изменения
  кода, типа или настроек самого свойства.
- Содержимое согласованных областей `/include/`, контакты и существующие статические меню
  через предназначенный для этого интерфейс. Сохранять структуру файлов и рабочие ссылки;
  изменения PHP-кода передавать разработчику.
- Загрузки через админку Битрикса. Файлы, на которые ещё ссылается контент, не удалять вручную.

### Что нельзя править через админку или прямо на сервере

- Управляемые файлы из таблицы выше: шаблоны компонентов, `header.php`, `footer.php`,
  CSS, JS, SVG и другие изображения оформления, `local/ajax/`, `local/php_interface/`,
  программные `*.menu_ext.php` и обновляемые `index.php` страниц.
- Параметры компонентов на этих страницах через визуальный редактор Битрикса.
  Сохранение параметров может переписать PHP-файл и создать расхождение с репозиторием.
- Содержимое `_dist`: это результат сборки, а не место для исправления стилей или скриптов.
- Код, тип, множественность и целевой инфоблок свойства; `XML_ID` вариантов списков;
  технические коды пользовательских полей и их типы. Эти изменения выполняет разработчик
  миграцией после проверки существующих данных.
- Привязки шаблонов сайта, адреса страниц инфоблоков, маршруты и технические настройки форм
  без согласования с разработчиком. Смена символьного кода раздела или услуги меняет URL:
  заранее проверить ссылки и необходимость перенаправлений.
- GitHub Secrets/Variables доставки, SSH-ключи, доступ по SSH, права файлов и содержимое
  служебного каталога доставки без согласования с ответственным за публикацию.

Ручная правка управляемого кода **останавливает следующий деплой**:
скрипт обнаружит несовпадение контрольной суммы. Не обходить эту проверку и не править
`current.json` для её подавления. Разработчик сохраняет серверную правку, сравнивает её
с Git и согласует перенос в репозиторий либо возврат к опубликованному коду.

Администратору не следует исправлять текст внутри PHP-шаблона, даже если он виден
в редакторе файлов. Такой текст сначала нужно вынести разработчиком в инфоблок,
свойство или редактируемую область, затем менять через интерфейс контента.

## Что разработчик синхронизирует отдельно

Исходный код переносится из Git в рабочий сайт. Актуальные рабочие данные и контент
редактируемых областей сохраняются на сервере. Они не синхронизируются в обе стороны
автоматически. Локальное наполнение не должно заменять последние правки редакторов,
новые заявки и пользователей.

| Локальное изменение | Действие разработчика для рабочего сайта |
| --- | --- |
| Новый инфоблок, свойство, пользовательское поле или вариант списка | Проверяемая идемпотентная миграция: код, тип, множественность, `XML_ID`, целевой инфоблок, обязательность и начальные значения. Существующие значения сохраняются |
| Новая привязка, выбор услуг для слайдера, тиззеров или меню | Определить, это первоначальная настройка релиза или последующая работа редактора. Первоначальную настройку переносить отдельно и только в согласованном объёме |
| Новая веб-форма или изменение её полей | Синхронизировать структуру формы, SID вопросов, ответы, обязательность, активность, права, почтовые события и шаблоны; проверить ID, используемые кодом |
| Новый раздел сайта, ЧПУ, языковая версия или смена URL | Проверить правила доставки файлов, `urlrewrite.php`, `.section.php`, меню, настройки сайта/инфоблоков, шаблоны и перенаправления. Git-код страницы сам по себе этого не создаёт |
| Текст, контакты, меню, логотип или файл области, изменённый только локально | Сверить с актуальной серверной версией и перенести согласованное изменение вручную или отдельной миграцией. Не копировать локальный `/include/` целиком |
| Новые изображения и документы, на которые ссылается наполнение | Перенести через Битрикс или согласованный импорт и проверить реальные ссылки `/upload/`; ID файлов локальной базы не считать серверными ID |
| Изменение прав, групп, шаблонов сайта, модулей, почты или окружения | Настроить отдельно на соответствующем окружении. Пароли, локальные хосты и пути не переносить в код |
| Обновление ядра Битрикса или модулей | Отдельная процедура с резервной копией и проверкой совместимости; обычная доставка приложения ядро не обновляет |

Для новых объектов предпочтительны поиск по коду и сопоставление вариантов по `XML_ID`.
Локальные ID инфоблоков, разделов, элементов, форм, вариантов списков и файлов могут
отличаться от серверных. Если проект опирается на фиксированный ID, проверить, что
на рабочем сайте он указывает на ожидаемый объект. Не переносить локальный дамп поверх
рабочей базы ради создания нескольких полей.

### Текущие поля услуг и тиззеров

Этот реестр описывает интерфейс, который использует код. При изменении схемы
разработчик обновляет миграцию и документацию вместе.

| Инфоблок / объект | Код | Ожидаемая настройка |
| --- | --- | --- |
| «Услуги» (5), элемент | `HERO_TIZZERS` | Множественная привязка к элементам «Тизеры» (29) |
| «Услуги» (5), элемент | `SEO_EYEBROW` | Одиночная строка; пусто → «об услуге» |
| «Услуги» (5), элемент | `SEO_TITLE` | Одиночная строка; пусто → «Подробно про услугу» |
| «Услуги» (5), элемент | `SHOW_IN_SLIDER_ON_LISTING_PAGE` | Одиночный список; вариант «Да» с `XML_ID = Y` |
| «Услуги» (5), раздел | `UF_HERO_TIZZERS` | Множественная привязка к элементам инфоблока 29 |
| «Услуги» (5), раздел | `UF_SHOW_IN_DESKTOP_MENU` | Одиночный флажок «Да/Нет»; код также поддерживает существующий список с вариантом `XML_ID = Y` |
| «Услуги» (5), раздел | `UF_PRICE_LINKED` | Одиночная привязка к разделу «Прайс-лист» (22) |
| «Прайс-лист» (22), раздел | `UF_SERVICE_LINKED` | Одиночная привязка к разделу «Услуги» (5) |

В «Тизеры» (29) общий набор находится в разделе «По умолчанию» (5158), остальные
элементы — в корне. Услуга и раздел выбирают тиззеры независимо; выбор раздела
не наследуется услугой. При пустом выборе или отсутствии доступных выбранных элементов
используется общий набор. Выводится до четырёх активных тиззеров по сортировке.

Меню ПК показывает до семи отмеченных разделов, последующие — в «Ещё».
Бургер-меню показывает все доступные активные разделы верхнего уровня независимо от флажка.
Поэтому шесть отметок дадут шесть пунктов, а пустой выбор услуг для слайдера не создаст
слайдер. Отмеченные для слайдера услуги исключаются из основной плитки раздела.
Название варианта «Да» само по себе не заменяет требуемый `XML_ID = Y`.

Связи услуг и цен нужно проверять в обе стороны: изменение `UF_PRICE_LINKED`
автоматически не заполняет `UF_SERVICE_LINKED`. Также проверить существующие привязки
FAQ, документов и связанных материалов, если задача их меняет.

Подготовленные операции:

- [hero-tizzers.php](local/php_interface/migrations/hero-tizzers.php) — поля привязок,
  перенос тиззеров в корень, сохранение общего набора и удаление опустевших старых разделов.
  [Подробное описание](local/tools/migrate-hero-tizzers.md).
- [service-display.php](local/php_interface/migrations/service-display.php) — отсутствующие
  поля меню, SEO и слайдера. Первоначальные отметки применяются только при создании
  соответствующего поля; существующий выбор редакторов сохраняется.
- [bind-service-price-sections.php](local/tools/bind-service-price-sections.php) — отдельная
  операция привязки разделов услуг и цен. `local/tools/` не входит в автоматическую
  доставку; наличие инструмента в Git не означает его наличия на сервере.

Первые две миграции доставляются как код в `local/php_interface/migrations/`.
Их **не запускает GitHub Actions**. Перед применением прочитать конкретный план и
проверить резервную копию; не запускать все имеющиеся миграции на каждом релизе.
Для текущих скриптов вызов без `--apply` показывает план. Например, на целевом сайте:

```sh
php -d short_open_tag=1 local/php_interface/migrations/service-display.php
php -d short_open_tag=1 local/php_interface/migrations/service-display.php --apply
```

Использовать PHP CLI нужной версии и каталог именно целевого сайта. Если схема нужна
новому коду сразу, заранее определить порядок применения: автоматический деплой
может завершиться раньше ручного запуска миграции. Для несовместимых изменений
нужны совместимый промежуточный релиз или согласованное окно обслуживания.

## Проверки разработчика перед публикацией

1. Сверить рабочую ветку с актуальным `main`, отделить относящиеся к задаче файлы
   от локального окружения, архивов и других веток. Проверить `git diff` и `git status`:
   в коммите не должно быть дампов, секретов, `/upload/`, локальных конфигов или
   случайных файлов незавершённой языковой версии.
2. Выполнить `npm ci`, `npm run build`, `npm test` в подходящем окружении.
   Проверить изменённые страницы в браузере, включая мобильную ширину.
3. Составить перечень изменений вне кода: свойства, `UF_*`, варианты списков,
   формы, начальные значения, маршруты, включаемые области, файлы и настройки.
   Для каждого указать, переносит ли его миграция, разработчик вручную или редактор.
4. Проверить существующие серверные значения и ссылки. Для миграций подготовить
   план применения, сохранения данных и восстановления; не удалять старое свойство
   или раздел до переноса всех используемых привязок.
5. Если добавляется новый путь доставки — проверить упаковку и серверный список
   разрешённых путей. Обновить документацию и тесты. Не считать новый каталог
   опубликованным только потому, что он попал в Git.
6. Проверить доступ GitHub runner к хостингу по SSH, соответствие ключа и
   `known_hosts`, актуальность настроек `production`, доступность сайта и место
   под резервную копию. Локальный успешный SSH не подтверждает доступ из Actions.
7. Отправить PR в `main`, дождаться обязательных проверок и слияния. Для предварительного
   просмотра запустить workflow `Site` с режимом `plan`; для повторной установки —
   `apply` только для актуального `main`. Эти операции выполнять в рамках согласованной
   публикации: слияние в `main` само запускает доставку при включённом флаге.

## Проверки разработчика после публикации

Успешный `Build and test` ещё не означает доставку. Успешный `Deploy production`
ещё не подтверждает применение ручных миграций и бизнес-сценариев.

1. Убедиться, что `Deploy production` завершился успешно для нужного коммита.
   На сервере сверить `current.json` и `last-success.json` в служебном каталоге,
   наличие завершённой копии `backups/<снимок>/data/complete.json` и отсутствие
   незавершённого журнала `pending.json`. Не удалять журнал вручную для продолжения.
2. Применить только миграции и ручные настройки данного релиза в определённом
   заранее порядке. Проверить созданные поля непосредственно в админке: код, тип,
   множественность, `XML_ID`, целевые инфоблоки, обязательность и выбранные значения.
   Убедиться, что последние правки редакторов и заявки сохранены.
3. Проверить главную, `/services/`, изменённый раздел и детальную услугу,
   `/prices/` и соответствующий раздел цен; при изменении материалов — новость,
   мероприятие или публикацию. Проверить ЧПУ, хлебные крошки, заголовки, взаимные ссылки,
   цены, изображения и документы. Несуществующий адрес должен вернуть HTTP 404.
4. На ПК и в бургер-меню проверить состав разделов, «Ещё», раскрытие и переходы.
   Проверить тиззеры с привязкой и без неё, распределение услуг между плиткой и
   слайдером, отсутствие дублей, заголовки, стрелки и свайп. Если отметок нет,
   отсутствие соответствующего блока является ожидаемым поведением.
5. Проверить формы на странице, в футере и модальных окнах: правильную форму,
   обязательные поля, согласие и ссылку `/privacy-policy/`, AJAX и отображение ошибок.
   Тестовую отправку выполнять согласованно; проверить запись в Битриксе,
   согласие и доставку письма, не полагаться только на сообщение «отправлено».
6. Открыть изменённые страницы без авторизации в новом сеансе и повторно с кешем.
   Проверить загрузку CSS/JS из нового манифеста, отсутствие ошибок браузера и PHP.
   Изменить в согласованном тесте значение свойства и убедиться, что связанный блок
   обновляется. При изменении include-областей проверить кеш компонента и страницы.
7. Проверить доступ редакторов к разрешённому контенту и права PHP на загрузки и кеш.
   Если затронуты OPcache, CDN или внешний HTML-кеш, проверить их отдельно:
   обычная очистка кеша Битрикса не гарантирует их обновление.
8. Зафиксировать коммит, результат доставки, применённые миграции, ручные действия
   и оставшиеся настройки редактора. Актуальные серверные изменения контента,
   структуры и разрешённых файлов при необходимости перенести в локальную среду
   отдельной согласованной операцией. Изменение схемы отразить в миграциях, а не
   оставлять только в локальной базе.

Автоматические HTTP-проверки используют URL и фрагменты текста из серверного
`config.json`: они проверяют доступность страницы, ожидаемый текст и явные PHP-ошибки.
Они не нажимают кнопки, не проверяют внешний вид, содержимое админки, отправку форм
и получение почты. Это остаётся отдельной проверкой разработчика.

При сбое сначала определить этап: тесты, подключение SSH, резервная копия,
контрольные суммы, установка или HTTP-проверки. Не отключать проверки ради публикации.
Если проблема в SSH, проверить доступ именно из runner, включённый доступ на хостинге,
IPv4/IPv6 и сетевые ограничения. Повторный запуск не требует изменения кода,
если причина была устранена настройкой доступа.

Откат приложения возвращает предыдущие файлы кода, но **не откатывает базу** и
выполненные вручную миграции. Проверить совместимость старого кода с новой схемой;
восстановление данных планировать отдельно с сохранением новых заявок и контента.
Команды отката описаны в [разделе восстановления](#откат-и-восстановление).

## Первое подключение сервера

Сначала завершите восстановление резервной копии и проверьте сайт в браузере.
Нужен Linux-сервер с SSH по ключу, Python 3.6+, PHP CLI 8.2+, `mysqldump` или `mariadb-dump`.
Серверные скрипты проверяются отдельно на Python 3.6 для совместимости с Timeweb;
сборка приложения и упаковка релиза выполняются на современном окружении GitHub Actions.
PHP CLI должен соответствовать версии PHP сайта. Проверьте доступ к базе из CLI.

Выделите пользователя доставки, например `usticom-deploy`. Он должен иметь права
на замену файлов приложения и чтение резервируемых данных. У PHP сайта должны остаться
права записи в `/upload/`, `/include/`, кеши, статические меню и другие разрешённые области.
На виртуальном хостинге, где PHP работает от владельца аккаунта, новые файлы получают
права `0644`, каталоги — `0755`. Общей группе хостинга права записи не выдаются.
Если у PHP отдельный пользователь, укажите специально выделенную группу через `--web-group`:
тогда новые файлы контента получают `0664`, каталоги контента — `2775`; код остаётся `0644`.
Для существующих файлов и каталогов права проверяются отдельно при настройке сервера.
Не выдавайте `0777` на весь сайт.

Пример структуры, пути заменяются фактическими:

```text
/home/client/www                 действующий корень сайта
/home/client/usticom-deploy      служебное состояние и резервные копии
```

Служебный каталог должен находиться вне дерева сайта, быть доступен только пользователю
доставки и иметь достаточно места для полной копии базы, Битрикса и загрузок перед каждым релизом.
Каталоги `backups` автоматически не удаляются. Настройте наблюдение за местом и перенос
копий на отдельное хранилище; удаляйте старые снимки только после проверки восстановления.

Скопируйте `deploy/` во временный приватный каталог на сервере и выполните от пользователя доставки:

```sh
python3 deploy/init-server.py \
  --root /home/client/www \
  --state /home/client/usticom-deploy \
  --url https://www.example.com \
  --web-group www-data \
  --php /usr/bin/php
```

Для Timeweb с PHP от владельца аккаунта не передавайте `--web-group www-data` из примера:
опустите этот параметр. Группу `newcustomers` для записи не используйте.
Скрипт создаёт `config.json` и постоянный `remote.py` в служебном каталоге.
Он не меняет сайт. Укажите фактическую группу PHP и версию CLI.
Проверьте `health_checks` в `config.json`: домен должен вести на нужный сервер,
пути — возвращать HTTP 200, поле `contains` — присутствовать на соответствующей странице.
Как минимум проверьте главную, контакты и цены. При необходимости добавьте конкретную услугу
и публикацию для проверки ЧПУ. Проверки должны проходить до и после релиза.
HTTPS-сертификат должен быть действительным.

Для GitHub Environment `production` настройте следующие значения:

| Тип | Имя | Значение |
| --- | --- | --- |
| Repository variable | `PRODUCTION_DEPLOY_ENABLED` | До окончания настройки `false`, затем `true` |
| Environment variable | `DEPLOY_HOST` | Адрес сервера, доступный GitHub runner |
| Environment variable | `DEPLOY_PORT` | Порт SSH, обычно `22` |
| Environment variable | `DEPLOY_USER` | Пользователь доставки |
| Environment variable | `DEPLOY_ROOT` | Абсолютный путь к действующему сайту |
| Environment variable | `DEPLOY_STATE` | Абсолютный путь к приватному служебному каталогу |
| Environment secret | `DEPLOY_SSH_PRIVATE_KEY` | Отдельный ключ доставки |
| Environment secret | `DEPLOY_SSH_KNOWN_HOSTS` | Проверенная запись ключа SSH-сервера |

Публичную часть ключа добавьте в `authorized_keys` пользователя доставки. Приватный ключ
передаётся только в GitHub Secret. Запретите forwarding и PTY для этого ключа через
`restrict` в `authorized_keys`, если версия OpenSSH поддерживает эту опцию.
Отпечаток ключа сервера сверяйте через панель хостинга или доверенный канал;
не отключайте `StrictHostKeyChecking`. Ограничьте environment `production` веткой `main`.
Для приватной сети потребуется runner с сетевым доступом; обычный GitHub runner туда не подключится.

После слияния workflow в `main` включите repository variable, запустите workflow вручную
в режиме `plan` и изучите список замен. План не создаёт резервную копию и не меняет сайт.
В `config.json` на сервере установите `allow_initial_deploy=true` только после проверки
первого плана. Затем вручную запустите `apply` для текущего `main`. После первого успешного
обновления верните `allow_initial_deploy=false` и проверьте права редакторов.
Дальше слияния в `main` доставляются автоматически.

Первый релиз не имеет истории контрольных сумм сервера: в нём особенно важно проверить,
какие файлы приложения заменяются. Перед заменой будет создана резервная копия.
Текущий сайт должен содержать настоящие `/include/phone.php`, `mail.php`, `address.php`
и `urlrewrite.php`; при их отсутствии доставка останавливается до загрузки кода.

Не обновляйте действующий сайт через `git pull`, `reset --hard` или полную синхронизацию
каталога с удалением лишних файлов. В этом изменении некоторые отслеживаемые файлы контента
удалены из Git: обычный checkout такого коммита может удалить их с диска.
Используйте архив релиза и скрипт доставки, который сохраняет серверные файлы.

## Что происходит при обновлении

1. CI выполняет `npm ci`, собирает Vite, проверяет PHP и запускает регрессионные тесты.
2. В архив включаются только разрешённые файлы кода, свежая сборка, начальные значения и скрипты доставки.
3. Доставка проверяет, что коммит ещё является текущим `main`. Одновременные доставки блокируются.
4. Сервер проверяет архив, контрольные суммы, отсутствие ручных изменений кода и синтаксис PHP.
5. Выполняются предварительные HTTP-проверки, создаётся копия заменяемого кода,
   дамп базы и архив изменяемых файлов вместе с Битриксом. При ошибке копирования обновление прекращается.
   Большой архив сжимается на быстром уровне gzip; каждые 20 секунд в журнале появляется
   сообщение о копировании. SSH поддерживает соединение во время длительных операций.
6. Отсутствующие области инициализируются; файлы кода заменяются через временный файл и rename.
   Удаляются только устаревшие файлы, ранее доставленные этим механизмом.
   Старые файлы `_dist` сохраняются для страниц, ещё использующих предыдущие хешированные URL.
7. Кеш Битрикса очищается, сайт проверяется по HTTP. При ошибке возвращается предыдущий код.

Обновление происходит в действующем каталоге: каждый файл заменяется атомарно, весь релиз — нет.
Во время загрузки возможен короткий переход между версиями; несовместимые изменения
планируйте на согласованное окно обслуживания. Для PHP OPcache нужно
`opcache.validate_timestamps=1` с небольшим `revalidate_freq`, либо отдельно настроенный
перезапуск PHP-FPM. Очистка OPcache из CLI не очищает кеш PHP-FPM.
CDN или внешний HTML-кеш требуют своей процедуры очистки.

При аварийном завершении процесса журнал `pending.json` блокирует последующую доставку.
Сохраните логи GitHub Actions и восстановите код командой `recover`.
Не восстанавливайте старую базу автоматически: это удалит новые заявки и правки.
Дамп с `--single-transaction` рассчитан на InnoDB; согласованное резервирование MyISAM
или внешних хранилищ нужно настроить отдельно до включения доставки.
Архив сохраняет вложенные символьные ссылки как ссылки: их внешние цели нужно резервировать отдельно.

## Откат и восстановление

На сервере от пользователя доставки:

```sh
python3 /home/client/usticom-deploy/remote.py rollback \
  --root /home/client/www --state /home/client/usticom-deploy
```

Это откат последнего успешного обновления кода. Перед ручным откатом текущий код
тоже сохраняется. База, новые загрузки и контент остаются текущими.
Если серверный код вручную изменён, сначала сохраните и согласуйте эти изменения:
автоматический откат остановится при расхождении контрольных сумм.

Для прерванной доставки:

```sh
python3 /home/client/usticom-deploy/remote.py recover \
  --root /home/client/www --state /home/client/usticom-deploy
```

После отката исправьте проблему и отправьте исправление отдельной веткой через pull request.
Старый коммит не доставляется поверх более нового `main`; аварийный откат выполняйте серверной командой.

Каждый снимок содержит `code.tar.gz`, `before.json`, `ops/` и `data/` с `database.sql.gz`,
`content.tar.gz`, `complete.json`. Для полной аварии восстановите их в отдельном каталоге
и тестовой базе, проверьте результат, затем планируйте переключение. Не распаковывайте старый
`content.tar.gz` поверх работающего сайта без оценки новых данных.

Документация GitHub: [защита веток](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches)
и [окружения доставки](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments).
